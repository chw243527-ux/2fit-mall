# 2FIT Mall 현재 버전 추가 보완 검토 보고서

검토 대상은 `main` 브랜치의 최신 커밋 `1b4becf`와 현재 저장소 상태입니다. 검토 범위는 웹 기능, 결제·주문, 재고, 권한·개인정보, 반응형 UI, PDF, CI/CD 및 운영 모니터링입니다.

## 종합 결론

현재 버전은 **빌드와 자동 배포 관점에서는 정상**입니다. 최신 커밋에 대해 Flutter CI, Security Audit, Release Security Verification, Android Play Internal Testing, Web Deploy가 모두 성공했습니다. 기본 보안 감사도 `Failures: 0 | Warnings: 0`으로 통과했습니다.

그러나 이것만으로 실사용 안정성을 확정할 수는 없습니다. 현재 운영 모니터는 공개 URL, 응답 시간, TLS와 보안 헤더를 확인하지만 로그인, Toss 결제 승인, 중복 주문 방지, Firestore 재고 차감, FCM 수신까지 자동 검증하지 않습니다. 결제·재고·권한·개인정보 항목은 실제 운영과 동일한 테스트 계정 및 테스트 상품으로 최종 검증해야 합니다.

따라서 현재 판정은 **조건부 승인**입니다. P0 시나리오 검증이 완료되기 전에는 결제와 재고 기능을 완전히 검증된 것으로 간주하지 않는 것이 안전합니다.

## 우선순위 P0: 출시 전에 반드시 확인할 항목

### 결제·주문 무결성

결제 취소 또는 실패 후 Checkout 화면으로 복귀했을 때 결제 버튼이 다시 활성화되는지 확인해야 합니다. 같은 결제 성공 콜백을 새로 고침하거나 다시 열어도 주문이 한 번만 생성되고 재고가 한 번만 차감되어야 합니다. 빠른 중복 클릭, 네트워크 지연, 결제 위젯 재진입도 함께 확인해야 합니다.

서버가 클라이언트가 보낸 상품 금액과 옵션 금액을 그대로 신뢰하지 않고 상품·재고·할인·배송비를 재계산하는지 확인해야 합니다. 장바구니에 담은 뒤 재고를 0으로 변경한 상품은 결제 승인되지 않아야 합니다.

### 재고·재입고 알림

관리자 재고 수정 후 `stockData`, `sizeStocks`, `stockCount`가 일관되게 저장되는지 실제 상품으로 확인해야 합니다. 일괄 재고 수정, 음수 입력 차단, 두 관리자 화면의 동시 수정, 0에서 양수로 복구하는 흐름을 확인해야 합니다.

재입고 알림은 동일한 신청자에게 중복 발송되지 않아야 하며, 발송 실패가 재고 저장 자체를 실패시키지 않아야 합니다. 알림을 클릭했을 때 해당 상품뿐 아니라 가능한 경우 색상·사이즈 선택 상태까지 복원되는지도 확인해야 합니다.

### 권한·개인정보

일반 계정으로 관리자 URL과 관리자 함수에 직접 접근할 수 없어야 합니다. 다른 사용자의 주문 ID, 배송지, PDF, 디자인·로고·허리밴드 첨부파일 URL을 알고 있어도 읽을 수 없어야 합니다. 로그아웃 후 뒤로가기와 브라우저 새로고침으로 이전 사용자의 정보가 노출되지 않아야 합니다.

관리자 claim을 회수한 뒤 기존 세션을 새로 고쳤을 때 관리자 메뉴와 쓰기 기능이 즉시 차단되는지도 확인해야 합니다.

## 우선순위 P1: 운영 안정성을 위해 다음으로 보완할 항목

### 작업 트리 정리

현재 작업 트리에 의도하지 않은 변경 파일이 남아 있습니다.

- Flutter 플러그인 생성 파일
- `pubspec.lock`
- `android/app/build.gradle.kts`
- `artifacts/`의 PDF·PNG 샘플
- `tool/generate_pdf_sample.dart`
- 미추적 문서 파일

이 중 빌드 과정에서 자동 생성된 파일은 저장소 기준과 비교해 원복하거나 필요한 변경만 별도 커밋해야 합니다. 샘플 산출물과 일회성 생성 도구는 저장소에 둘 필요가 없으면 제거하고 `.gitignore` 정책을 정해야 합니다. 작업 트리가 깨끗하지 않으면 다음 배포에 의도하지 않은 플랫폼 파일이나 테스트 자료가 포함될 수 있습니다.

### 정적 분석 경고 정리

전체 `flutter analyze`는 오류 없이 실행되지만 종료 코드는 1이며 총 2,140개 항목이 보고되었습니다. 현재 집계상 warning 146건, info 1,994건입니다. 보안 게이트는 허용된 분석 항목을 통과시켰지만, 이 규모의 경고는 실제 오류를 가릴 수 있습니다.

특히 다음 영역부터 정리하는 것이 좋습니다.

1. `group_order_form_screen.dart`의 미사용 주문서·허리밴드 UI 메서드
2. `order_excel_service.dart`의 미사용 PDF 스타일·헬퍼
3. `notification_service.dart`의 미사용 알림 상태 필드와 메서드
4. 결제 화면의 미사용 import와 상태 변수
5. 관리자 화면의 광범위한 `catch (e)` 및 예외 처리 경로

신규 코드에는 오류·경고 0개 기준을 적용하고, 기존 항목은 파일별로 허용 목록을 관리하는 방식이 안전합니다.

### 주소·주문자 데이터 일치

주소 저장 시 주소, 우편번호, 상세주소, 현재 주문자명, 전화번호가 함께 저장되는지 확인해야 합니다. 저장된 주소를 다시 선택했을 때 주문자명과 전화번호가 자동 입력되어야 합니다. Checkout, 주문 문서, 관리자 상세, PDF의 값이 서로 다른 저장 키 때문에 달라지지 않는지도 확인해야 합니다.

### 단체주문 PDF와 관리자 상세

싱글렛, 싱글렛 세트, 라운드티, 타이즈, 기타 단체주문 상품을 각각 테스트해야 합니다. 선택하지 않은 옵션은 표시되지 않아야 하고, 선택한 색상명·HEX·실제 색상, 디자인·로고·허리밴드 첨부파일, 디자인 수정 메모와 전화번호가 주문서·관리자 화면·PDF에 동일하게 표시되어야 합니다.

업로드하지 않은 파일은 빈 카드나 깨진 링크 없이 미표시되어야 하며, 10명 이상 팀원과 긴 이름에서도 표가 깨지지 않아야 합니다.

## 우선순위 P2: 품질과 사용성을 높이는 추가 기능

### 운영 알림 채널 확대

현재 모니터링 실패는 GitHub Issue와 저장소 알림으로 처리됩니다. 운영자가 즉시 확인해야 한다면 Slack, 이메일, SMS 또는 카카오 알림을 별도 Webhook/API 비밀값으로 연결할 수 있습니다. 비밀값은 저장소 코드나 로그에 기록하지 않아야 합니다.

### 결제·주문 관측성 강화

결제 시작, 결제 성공, 결제 취소, 결제 실패, 주문 생성, 재고 차감에 상관관계 ID를 부여하면 장애 조사 시간이 줄어듭니다. 로그에는 전화번호·주소·토큰·결제 민감정보를 포함하지 않고 주문 ID의 일부만 기록하는 것이 좋습니다.

### 이미지 및 배너 성능

상품 이미지와 배너 영상은 실제 iPhone Safari, Android Chrome, 태블릿 브라우저에서 첫 표시 시간과 자동재생 성공 여부를 확인해야 합니다. 이미지 실패·느린 네트워크·Service Worker 갱신 후에도 레이아웃이 유지되어야 합니다. 배너 동영상은 재생 컨트롤이 표시되지 않고, 동영상은 10초, 일반 배너는 5초 후 전환되며 사용자의 스와이프가 우선되는지 확인해야 합니다.

### 롤백과 백업 리허설

직전 안정 커밋으로 웹을 되돌리는 절차와 Firebase 데이터·Storage 첨부파일 복구 절차를 실제로 한 번 리허설하는 것이 좋습니다. 백업 문서만 존재하고 실제 보호 버킷, 보존 기간, IAM 권한, 복구 테스트가 없는 경우에는 장애 시 복구를 보장할 수 없습니다.

## 바로 실행할 권장 순서

1. 테스트 계정과 테스트 상품으로 결제 취소·재시도·중복 클릭·품절 결제를 확인합니다.
2. 관리자와 일반 사용자 두 계정으로 재고 0→양수, 일괄 수정, 재입고 알림을 확인합니다.
3. 일반 계정으로 관리자 데이터와 다른 사용자의 주문·첨부파일 접근 차단을 확인합니다.
4. 주소 저장·선택 후 주문자명과 전화번호가 주문·관리자·PDF까지 일치하는지 확인합니다.
5. 단체주문 카테고리별 PDF와 관리자 상세를 검증합니다.
6. 작업 트리의 자동 생성 파일과 샘플 산출물을 정리합니다.
7. 정적 분석 warning을 P1 파일부터 줄이고 경고 기준을 CI에 고정합니다.
8. 실제 기기에서 360px, 390px, 768px, 1024px, 1280px 이상 너비를 점검합니다.

## 최종 판정 기준

결제 금액 불일치, 성공 후 주문 미생성, 중복 주문, 재고 과다 차감, 품절 구매, 타인 개인정보 노출이 하나라도 발생하면 출시를 보류해야 합니다. 해당 항목이 모두 통과하고 기록이 남으면 단계적 실사용 공개가 가능합니다. 반응형·성능·정적 분석 경고만 남은 경우에는 조건부 승인으로 운영할 수 있으나, P0 데이터 무결성 검증을 끝낸 뒤 진행하는 것이 안전합니다.
