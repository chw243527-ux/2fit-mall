# 2FIT Mall 현재 구현 기능과 향후 핵심 기능 비교

**검토 기준 커밋:** `75e06f2`
**검토 범위:** Flutter Web, Firebase, 결제·주문·재고, 관리자, 단체주문, 운영 자동화
**판정 기준:** 코드에 구현된 흔적이 있는 기능과 실제 운영 환경에서 합격이 확인된 기능을 구분합니다.

## 1. 전체 결론

2FIT Mall은 단순한 상품 진열형 쇼핑몰을 넘어 **기성품 판매, 기능성 상품 옵션, 단체주문, 결제, 재고, 관리자 운영, PDF 주문서, 알림**까지 포함하는 운영형 쇼핑몰 구조를 갖추고 있습니다.

현재 가장 중요한 차이는 기능의 존재 여부보다 **운영 신뢰성의 증명 수준**입니다. 결제·재고·권한·장바구니·단체주문 첨부파일과 같은 핵심 흐름은 코드와 자동 테스트가 상당 부분 구현되어 있지만, 실제 운영 데이터와 실제 기기에서 모든 시나리오가 합격했다고 보기는 어렵습니다.

| 구분 | 현재 판단 |
|---|---|
| 상품·카테고리·상품 상세 | 핵심 기능 구현 |
| 회원·소셜 로그인 | 구현되어 있으나 Kakao iPhone/Web 실기기 검수 필요 |
| 장바구니·옵션 보존 | 구현되어 있으나 복수 색상·사이즈 조합의 운영 검수 필요 |
| 결제·주문 | 서버 검증 및 재고 예약 구현, 실제 결제·취소·중복 호출 검수 필요 |
| 재고·품절·재입고 알림 | 관리 기능과 서버 로직 구현, 실데이터 반영 및 알림 수신 검수 필요 |
| 단체주문 | 핵심 옵션·첨부·PDF·관리자 상세 구현, 카테고리별 최종 대조 필요 |
| 관리자 | 상품·주문·재고·정산·쿠폰·리뷰·배송 등 핵심 화면 구현 |
| 보안·CI/CD | 보안 감사와 품질 게이트 구현, custom lint 실행 신뢰성 보완 필요 |
| Android 배포 | 최종 배포 전 상태. Google Play가 `minSdk 23` AAB를 거부함 |
| 추가 사업 기능 | CRM, 고급 검색·추천, 운영 분석, 자동화된 환불·교환, 백업 리허설 등 확장 필요 |

### 2.7 보안·품질·운영 자동화

| Web 배포 | Web Deploy workflow 구현 | 배포 후 smoke test, 캐시·Service Worker 갱신 확인 필요 |
| Android 배포 | Android workflow 및 AAB 생성 구현 | Play가 minSdk 23을 거부하므로 24 이상 수정 후 재검증 필요 |
| 모니터링 | 운영 URL·응답·TLS·보안 헤더 중심 모니터링 | 결제·로그인·재고·FCM까지 포함한 합성 모니터링 필요 |

## 3. 앞으로 추가할 핵심 기능

아래 기능은 현재 기능을 대체하는 것이 아니라, 쇼핑몰을 안정적인 상용 운영 서비스로 확장하기 위한 다음 단계입니다.

### 3.1 출시 직전 반드시 완성할 기능

이 항목은 새로운 사업 기능이라기보다 현재 구현 기능의 운영 완성도입니다.

1. **결제 멱등성 및 재시도 보장**: 결제 성공 callback을 반복해도 주문과 재고가 한 번만 처리되어야 합니다.
2. **재고 일관성 보장**: 관리자 수정, 공개 상품, 장바구니, 결제 승인, 재입고 알림이 같은 옵션별 재고를 사용해야 합니다.
3. **재입고 알림의 정확성**: 신청자·옵션별로 한 번만 발송하고, 알림 실패가 재고 저장을 막지 않아야 합니다.
4. **권한 경계의 실증**: 일반 사용자가 관리자 화면, 다른 주문, 다른 첨부파일, 관리자 함수에 접근하지 못해야 합니다.
5. **단체주문 데이터 보존**: 옵션·팀원·색상·첨부·PDF가 장바구니부터 관리자 주문 상세까지 동일해야 합니다.
6. **iPhone Web 결제·Kakao 로그인**: 실제 Safari에서 callback, 결제 취소, 결제 복귀, 세션 복원을 완성해야 합니다.
7. **CI 검사 신뢰성**: custom lint 도구가 없을 때 성공하지 않도록 해야 합니다.
8. **Android 배포 차단 해결**: `minSdkVersion 24 이상`과 Play Internal Testing 성공을 확인해야 합니다.

### 3.4 운영·분석 기능

현재 analytics service는 존재하지만, 상용 운영에는 화면과 지표가 더 필요합니다.

- 방문자, 상품 조회, 옵션 선택, 장바구니 담기, Checkout 진입, 결제 성공률을 단계별로 집계합니다.
- 상품·카테고리·색상별 매출과 재고 회전율을 표시합니다.
- 단체주문 문의에서 신청부터 결제·제작·배송 완료까지의 전환율을 표시합니다.
- 결제 실패 원인을 PG 오류, 사용자 취소, 재고 부족, 서버 검증 실패로 분류합니다.
- 알림 발송 성공률, 실패율, 클릭률을 표시합니다.
- 관리자 작업에 감사 로그를 남겨 재고·가격·주문 상태 변경을 추적합니다.
- 오류와 성능 지표에 상관관계 ID를 붙여 결제·주문 장애를 추적합니다.
- 개인정보를 제외한 구조화 로그와 운영 대시보드를 제공합니다.

### 3.5 안정성·복구 기능

- Firestore와 Storage 백업 정책, 보존 기간, 복구 담당자를 확정합니다.
- 직전 웹 버전 롤백을 실제로 리허설합니다.
- 주문·결제·재고 이벤트를 재처리할 수 있는 관리자 도구를 준비합니다.
- 외부 PG·FCM·Kakao 장애 시 사용자에게 재시도 가능한 안내를 제공합니다.
- 이미지·배너 CDN 실패 시 placeholder와 재시도 동작을 제공합니다.
- 네트워크가 끊겼다가 복구될 때 중복 주문이 발생하지 않도록 상태를 복원합니다.
- 운영 장애 알림을 GitHub Issue 외에 이메일, Slack, SMS 또는 카카오 알림으로 확장합니다.

### 3.6 법적·정책 기능

- 개인정보 수집·이용·보관·파기 정책을 실제 사업 운영 기준으로 확정합니다.
- 주문 취소·환불·교환·제작 상품의 청약철회 제한을 사용자에게 명확하게 표시합니다.
- 단체주문 디자인·로고·팀원 정보의 보관 기간과 삭제 정책을 명시합니다.
- 미성년자·주니어 상품 주문 시 필요한 고지와 동의 정책을 검토합니다.
- 광고성 알림과 거래성 알림을 구분하고 수신 동의·철회 이력을 관리합니다.
- 사업자 정보, 고객센터, 통신판매 관련 고지를 실제 사업자 정보와 일치시킵니다.

## 5. 현재 구현과 향후 기능의 관계

현재 구현은 **판매 가능한 기본 운영 사이클**을 구성합니다.

```text
상품 등록
→ 상품·옵션 선택
→ 장바구니
→ 주소·주문자 입력
→ 결제
→ 서버 주문 검증·재고 예약
→ 주문 상세·관리자 처리
→ 배송·알림
```

앞으로 필요한 기능은 이 사이클을 크게 바꾸기보다 다음 네 가지를 강화합니다.

1. **정확성:** 결제·재고·주문·옵션 데이터가 언제나 일치하도록 합니다.
2. **운영성:** 교환·환불·배송·정산·감사 이력을 자동화합니다.
3. **전환성:** 검색·추천·쿠폰·리뷰·CRM으로 구매율과 재구매율을 높입니다.
4. **복원성:** 외부 서비스 장애와 데이터 오류가 발생해도 안전하게 재시도·복구합니다.

## 6. 최종 권장 실행 순서

1. Android `minSdk 24`와 custom lint 실행 문제를 수정합니다.
2. Flutter 테스트, 정적 분석, 보안 감사, Web Deploy를 다시 통과시킵니다.
3. 실제 운영 계정으로 결제 성공·취소·실패·중복·품절 시나리오를 확인합니다.
4. 실제 운영 상품으로 재고 수정·일괄 적용·0→양수·재입고 알림을 확인합니다.
5. 일반 계정의 관리자·주문·첨부파일 접근 차단을 확인합니다.
6. iPhone Safari에서 Kakao 로그인과 Toss 결제 복귀를 확인합니다.
7. 단체주문 카테고리별 옵션, 첨부, 관리자 상세, PDF를 비교합니다.
8. PC·태블릿·모바일에서 장바구니·Checkout·마이페이지·관리자 화면을 확인합니다.
9. 반품·교환·부분 환불·운송장·감사 로그를 P1 확장 개발로 진행합니다.
10. 검색·추천·CRM·분석·복구 리허설을 P2 로드맵으로 진행합니다.

## 7. 한 줄 판단

**2FIT Mall은 상품 판매부터 주문·재고·관리까지의 핵심 뼈대는 구현되어 있습니다. 이제 가장 먼저 해야 할 일은 기능을 무작정 늘리는 것이 아니라, 결제·재고·권한·단체주문 데이터의 운영 합격을 확정하고, 그 다음 반품·배송·검색·추천·CRM·분석을 단계적으로 추가하는 것입니다.**
