## 핵심 결론

현재 쇼핑몰의 회원가입 본인확인은 **NICE아이디 본인확인(CI/DI) 연동이 아니라 Firebase Phone Auth 기반 SMS OTP 인증**입니다. SMS 발송·코드 확인 UI는 구현되어 있고, 코드 검색상 NICE 모듈, CI, DI, 인증결과 암호화 저장은 발견되지 않았습니다. 따라서 첨부된 양식에서 NICE CI/DI를 전제로 한 항목은 단순히 ‘저장하지 않는다’는 이유만으로 적합이 되는 것이 아니라, **해당 본인확인 연동 자체가 없는 상태**로 판단해야 합니다.[1]

가장 우선순위가 높은 문제는 SMS 인증 성공이 실제 이메일/비밀번호 회원 계정에 서버 측으로 결속되지 않는다는 점입니다. OTP 검증 함수는 인증 자격증명으로 임시 로그인한 뒤 그 계정을 삭제하고 `verified` 상태만 반환합니다. 가입 화면은 이 결과를 `_phoneVerified`라는 클라이언트 메모리 변수에 기록하고, 별도 `phoneVerified`, 검증 전화번호, 검증 시각, 서버 서명 결과를 `register()`로 전달하거나 서버에서 확인하지 않습니다.[2] [3] 웹 클라이언트는 수정하거나 우회할 수 있으므로, 가입 시 ‘SMS 인증 필수’는 현재 **화면 수준의 제어**일 뿐 서버가 강제하는 본인확인이 아닙니다.

또한 비로그인 상태에서 `https://2fit-mall.co.kr/#/admin`에 직접 접속했을 때 로그인 화면으로 이동하지 않고 관리자 대시보드 UI와 주문·회원·매출 메뉴가 표시되었습니다. 데이터베이스와 서버 기능에는 관리자 Custom Claim 기반 검사가 있어 실제 데이터 접근·변경은 상당 부분 차단되도록 되어 있지만, 첨부 양식의 ‘인증이 필요한 중요 페이지 접근 통제’에는 미달합니다.[4] [5]

## 체크리스트별 판정

| 번호 | 첨부 항목 | 판정 | 코드·운영 확인 근거 | 필요한 조치 |
|---:|---|---|---|---|
| 1 | **불필요한 중요정보 평문 노출** | **조건부 적합** | 회원가입 저장값은 이름·이메일·전화번호이며, 코드상 NICE CI/DI 및 인증 모듈 값은 수집·저장되지 않습니다. 비밀번호는 Firebase Auth에 전달되며 사용자 문서에 저장되지 않습니다.[1] [3] 다만 전화번호·배송정보 등 개인정보는 Firestore에 평문 속성으로 저장되므로 접근 권한과 필드 통제가 핵심입니다. | NICE 연동 시에는 CI/DI 원문을 클라이언트·Firestore·로그에 넣지 말고, 꼭 필요할 경우 서버의 암호화 저장소 또는 일방향 식별값 설계를 적용해야 합니다. 결제·주문 로그에도 전화번호·주소 전체가 남지 않는지 별도 점검하십시오. |
| 2 | **파라미터 변조** | **미흡** | 사용자 문서 생성 규칙은 로그인 사용자와 문서 ID 일치, `isAdmin=false`, 포인트 직접 설정 차단을 수행합니다.[5] 그러나 가입 검증 상태·검증 전화번호·이메일 인증 여부를 요구하지 않고, 사용자 본인은 `isAdmin`·`points` 외 필드를 사실상 자유롭게 수정할 수 있습니다. `isValidUserData()`의 필드 수 제한 함수도 실제 생성 규칙에서 사용되지 않습니다.[5] | 회원 프로필의 허용 필드를 명시적으로 화이트리스트화하고, `email == request.auth.token.email` 및 인증 완료 상태를 서버에서 검증하십시오. CI/DI가 도입되면 응답값의 서명·거래번호·요청 시각·서비스 ID·중복 여부를 서버에서 검증해야 합니다. |
| 3 | **입력정보 일치여부** | **미흡** | 가입 폼은 SMS 인증 완료 뒤 전화번호 입력을 잠그지만, `register()`는 일반 전화번호 문자열만 검증하고 OTP로 확인된 번호와의 일치 여부를 검사하지 않습니다.[2] [3] 이메일 검증 헬퍼는 규칙에 존재하지만 실제 사용자 접근 제어에 사용되지 않았고, 이메일 인증 발송 호출도 찾지 못했습니다.[5] | Firebase Phone Auth를 이메일/비밀번호 계정에 `linkWithCredential`로 연결하거나, 서버가 검증 토큰을 일회성으로 교환하여 UID·E.164 전화번호·검증시각을 저장하십시오. 가입·중요 기능에서 `phone_verified_at` 및 `email_verified`를 서버 측으로 확인하십시오. |
| 4 | **데이터 재사용** | **미흡** | SMS `verificationId`는 화면 메모리에만 존재하고, 인증 직후 임시 Firebase 계정을 삭제합니다. 애플리케이션 자체의 인증 결과 거래번호·소비 기록·재전송 제한·일회성 교환 검증은 없습니다.[2] Firebase 제공자 내부의 OTP 만료·실패 제한에 의존하는 구조입니다. | 서버에서 단발성 nonce/거래번호를 발급하고, 검증 성공 후 UID와 결속한 뒤 즉시 소진 처리하십시오. 가입 요청별 만료 시간, 재시도 횟수, 전화번호·IP·기기 기준 요청 제한, 감사 로그를 두십시오. |
| 5 | **암호키/모듈 노출** | **대체로 적합** | 결제 비밀키는 앱 상수에 빈 값으로 두고 서버 비밀값을 사용하는 구조이며, 결제 승인도 서버에서 주문 ID·금액·사용자 ID를 비교합니다.[6] 저장소에서 NICE 인증 모듈·키는 발견되지 않았습니다. | NICE를 붙일 경우 NICE client secret·site code·암호키를 웹 번들, GitHub, 앱 상수에 넣지 말고 서버 비밀값으로만 운영하십시오. 비밀값 스캔과 키 교체 절차를 CI에 추가하십시오. |
| 6 | **프로세스 검증 누락** | **미흡** | Firestore 및 서버 함수는 관리자 권한을 Firebase Auth Custom Claim으로 검사하고 주문·쿠폰 등 민감 데이터의 직접 생성을 제한합니다.[5] 하지만 전역 라우트는 `/admin` 요청 시 권한 검사 없이 `AdminScreen`을 생성하며, 운영 화면에서도 비로그인 방문자에게 관리자 UI가 노출되었습니다.[4] | 라우터 단계에서 로그인·관리자 Claim을 확인하여 미인가 사용자는 로그인 또는 홈으로 즉시 전환하십시오. `AdminScreen` 내부에도 이중 가드를 두고, 중요 페이지·API·파일 경로별 인가 테스트를 자동화하십시오. |
| 7 | **안전한 통신 프로토콜 사용** | **적합(관찰 범위)** | 운영 도메인은 유효한 인증서로 TLS 1.2 협상에 성공했고, TLS 1.1 연결은 암호군 협상에 실패했습니다. 응답에는 `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`가 적용돼 있습니다.[7] | 운영 응답에서 HSTS 및 CSP가 확인되지 않았습니다. 저장소의 Firebase 설정에는 HSTS가 있지만 실제 운영 도메인은 Netlify/Cloudflare 설정을 따르는 것으로 보여, 배포 설정을 일원화하고 `Strict-Transport-Security` 및 서비스에 맞춘 CSP를 운영 응답에서 재검증하십시오.[8] |

> **판정 기준:** ‘조건부 적합’은 현 구조에서 해당 위험을 직접 만들지 않지만 본인확인 연동이 아직 없거나 운영 설정의 최종 검증이 남은 경우입니다. ‘미흡’은 첨부 체크리스트에 ‘예’로 답하면 안 되는 항목입니다.

## 잘 적용된 부분

회원가입 화면에는 SMS OTP 발송·만료·코드 확인 인터페이스가 있고, 가입 버튼은 화면 기준으로 인증 완료 전 비활성 흐름을 갖습니다.[2] 결제의 경우에는 클라이언트가 전달한 금액을 그대로 신뢰하지 않고, 서버가 주문을 준비하고 결제 승인 때 결제대행사 응답의 주문 ID와 총액을 비교하는 구현이 확인됩니다.[6] 또한 Firestore의 주문 생성은 일반 클라이언트에 열려 있지 않으며, 관리자 판단은 사용자 문서의 `isAdmin` 값이 아니라 Firebase Custom Claim을 사용합니다.[5]

이 장점들은 유지할 가치가 있습니다. 다만 본인확인은 **화면에서 체크하는 것**이 아니라, 서버가 검증 결과를 해당 가입 주체에 묶고 이후 모든 중요 동작에서 그 결과를 재검증하는 구조여야 합니다.

## 다음 단계 제안

가장 안전한 진행 순서는 먼저 P0 두 건을 수정한 다음, ‘NICE CI/DI가 법적·계약상 꼭 필요한지’와 ‘휴대폰 소유 확인만 필요한지’를 확정하는 것입니다. NICE 도입이 필요하다면 현재 Firebase OTP 임시계정 삭제 방식에 덧붙이는 것이 아니라, 서버 전용 인증 세션을 새로 설계하는 편이 낫습니다. 이후 실제 운영 환경에서 Firebase Auth 제공자 설정, Firebase Rules 배포본, Functions 비밀값, Netlify/Cloudflare 헤더를 함께 확인해야 최종 ‘적합’ 판정을 할 수 있습니다.
